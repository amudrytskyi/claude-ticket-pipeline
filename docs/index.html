Ticket pipeline, reference

How the ticket pipeline works

A Claude Code setup that takes one ticket, or several, from issue to reviewed, fully tested, uncommitted code with a ready commit message and PR description, and learns from every run. It is made of 9 skills, 13 agent types, 2 hooks, 3 helper scripts and one workflow script. Everything lives in ~/.claude/ and in one git-excluded profile per repository; nothing is added to the codebase. State as of 5 November 2026, evening. Since the first version of this page: verification classifies every failure before a fix round, the guard sees through test wrappers, the profile keeps long local runs alive, and every statement below was checked against the installed files, the transcripts and the run log.

The shape

  • Phases hand off through files, never through chat. Every phase is a fresh agent that reads the files the previous phase wrote in a work directory outside git. Any phase can be re-run alone, by hand or by the workflow, without losing context.
  • Finders never fix; fixers never certify. Plan reviewers, code reviewers, the verifier and the PR-feedback reader only write reports. A different, fresh agent applies what they found, and the next fresh reviewer checks that.
  • Tests are tiered. Implementation runs only fast checks. Code review runs nothing. Verification runs the full matrix once, on the final tree.
  • Two gates. Gate 1 is automated and sits before any code is written: the plan review has stopped finding serious problems. Gate 2 is a person: nothing in the pipeline commits or pushes.
  • Rules are enforced, not just written. A hook checks every shell command and file write a pipeline agent makes. A second hook stops a reviewer from finishing without its report in the required form.
  • It learns from evidence, and a person decides. A retro after every run turns repeated misses into lesson candidates. A weekly pulse reads what everyone merged. Both only propose edits.

Three modes

Ticket

Default. "#123" or { input: "#123 <links>" }

Plan → plan review loop → implement → code review loop → verify loop → git texts → retro.

PR feedback

{ mode: "pr-feedback", input: "#123", pr: 456 }

Read the PR's comments and CI, read only → classify each against the code → a fix round → code review → verify → git texts for the fix round → retro.

Multi

{ mode: "multi", tickets: ["#1", "#2"] }

Overlap check → every ticket planned and plan-reviewed in parallel → tickets built one at a time, in the given order, each on its own branch, with a stop for the person's commit between them.

Step by step (ticket mode)

Each step is a separate agent. Its type sets the tools it has and what the guard lets it do. The agent receives the skill file as text and returns a structured result that the workflow checks against a schema.

0

Load the profile every phase

Every skill starts by reading .claude/pipeline.local.md. If it is missing, the phase stops and asks. The profile tells every phase to read the ## Now section of repo-knowledge.md, which the weekly pulse keeps, before relying on the runtime, a command or the stack. The skills themselves do not name that file, so the line belongs in every profile.

1

Plan pipeline-planner-artifacts plan-ticket

Reads the ticket, its parent epic, linked design notes and every artifact link, then the code along its real control flow. Writes <t>-analysis.md (surface, invariants checked, races and edge cases, out-of-scope defects listed, not folded in) and <t>-plan.md, the specification. Plan sections:

  1. Status and blockers
  2. Acceptance criteria (drafted ones marked "prepared, not posted")
  3. Evidence for each load-bearing claim
  4. Design
  5. Per-file changes
  6. Tests: per criterion, an assertion that fails without the change; one per property, each checked against a mutant
  7. Tests by phase
  8. Risks
  9. Decisions and open questions
  10. Base branch and its SHA
  11. Ticket text, prepared
  12. Commit and PR text, prepared

Prototypes run in a scratch worktree, never in the open checkout, so several tickets can be planned at once. Returns planPath, baseSha, readiness, artifactLinks. The first planner always gets the Artifact tool; if it finds links, every later phase gets it too.

2

Review the plan pipeline-plan-reviewer review-plan

A fresh reviewer per round reads the ticket and the code first and writes its own Expectations before opening the plan. Then the plan, then the planner's analysis and earlier responses, last. It re-runs the plan's targeted checks (never the full suites), applies one-line mutants to the plan's tests in a scratch copy, and hunts for what the plan does not mention: invariants, races, retries, partial failures, interface drift, scope drift, untracked files, sibling tickets.

It appends ## Round N to <t>-plan-review.md: Expectations, a Base line (base drift recorded as information), every earlier finding re-checked (resolved, still open, regressed), new findings F1… with severity, failure scenario, evidence, verdict (CONFIRMED / PLAUSIBLE / REJECTED) and the exact plan change, then two fixed lines:

Counts: new C/H/M/L n/n/n/n; open C/H/M/L n/n/n/n and Verdict: READY | NOT READY

Revise pipeline-planner plan-ticket revise: when anything is open, a different fresh planner decides every open finding: ACCEPTED (folded into the plan), REJECTED (only with evidence it ran or read), or DEFERRED (Medium and Low only). It appends a Planner response under the round. The next review round checks what it did. Up to maxPlanRounds = 4 rounds.
G1

Gate 1 automated

newCritical = newHigh = openCritical = openHigh = 0 in the latest round. Medium and Low may stay open: the planner folds them or records a decision, and the log says their folds were not re-reviewed. If the gate is not closed after 4 rounds, the run stops and logs new and open counts per round, so a person can see whether more rounds would help. To accept the plan anyway, the person resumes the run with acceptPlan: true.

3

Implement pipeline-implementer implement-plan

Works in the checkout the person has open, so the diff shows up in their editor. One implementation per checkout: if the tree holds another ticket's uncommitted work, the agent stops. Before editing it checks whether the base has moved since the plan's SHA. If any file the base changed is one the plan touches, it stops with baseMoved and does not edit. It re-runs the reproductions the plan cites; every disagreement with the plan goes into <t>-impl-findings.md with the command and its output, instead of being papered over in code.

Fast checks only: lint, unit tests related to the changed files, the new tests. An integration suite runs only when the plan names it as the only proof of a criterion. Never commits. It prepares the plan's commit and PR text.

4

Review the code pipeline-code-reviewer review-code

Records HEAD and takes the change as tracked edits plus untracked files (git ls-files --others), because git diff does not show new tests and migrations. It builds a table with one row per acceptance criterion: the file:line that satisfies it, the test that would fail without it, and CLOSED / PARTIAL / NOT CLOSED. A criterion with no test is at best PARTIAL. Then it checks what the criteria do not cover: invariants, races, leaks, tests that cannot fail, docs obligations. It runs no suites; a single test only when needed to decide a criterion. It re-checks HEAD before its verdict. Writes <t>-code-review.md, ending Verdict: ALL ACS CLOSED | GAPS.

On GAPS: a fix round whose prompt lists the open findings and criteria, as pointers into the report, then a fresh code review. Up to maxFixRounds = 2; after that the run stops at review-code.
5

Verify pipeline-verifier verify-ticket effort low

First, read only, it checks the base: the merge base with the plan's base branch and the base's own CI results. Jobs already red there are recorded as known base failures. Then it runs the profile's full matrix once, in order, on the exact tree it records (HEAD, status, untracked), with the long steps kept awake the way the profile says. Each step runs on the stack the profile names. Suites that reset their database run on a throwaway stack the verifier starts, points at in the same command, leak-checks and removes, also on failure. A step that cannot run is BLOCKED, never "passed".

Every failure that is not a known flaky test is classified, in this order:

  • environment: the host slept during the step, or the error matches one of the profile's environment signatures. Only those tests are re-run once, awake and alone. If they pass, the run is not RED and the failure is named. If they fail the same way, the verdict is BLOCKED.
  • base: the test and the code it exercises lie outside the change, and the failure is a known base failure or reproduces on a detached worktree of the merge base.
  • change: everything else, and anything unclear.

Writes <t>-verify.md: the base check, a table of steps (command, exit code, counts, minutes), each failure with its class and the evidence for it, and Verdict: GREEN | RED | BLOCKED.

On RED with change failures: a fix round that re-runs only those tests, then verification again. Up to maxVerifyFixes = 2. These fix rounds skip code review; gate 2 is where a person sees them. On RED with only base failures: no fix round; the run stops with verify-base-red. On BLOCKED: the run stops so the environment can be fixed.
6

Git texts pipeline-planner plan-ticket git-texts effort low

Runs whenever code changed, whatever the verdict. Starts from the plan's commit and PR section, makes the Changes list match the real diff, and fills Testing from the verify report, step by step with commands and counts. A step that did not run or failed is said as such. Writes <t>-git-texts.md: commit message, PR title, PR description, ready to paste. The last log line of the run names this file.

7

Retro pipeline-retro effort medium

Runs at the end of every run, finished or stopped. It measures with runstats.py and reads the handoff files. It appends one JSON line to pipeline-runs.jsonl, finds escapes and updates lesson candidates. Details under Learning loops.

G2

Gate 2 a person

The person reads the diff and the git-texts file, then commits and opens the PR. The guard refuses these for pipeline agents, in the forms it can parse (see The guard). After the PR gets comments or red checks, PR-feedback mode turns them into the next round.

PR-feedback mode

The pipeline-pr-feedback agent reads the PR read only: state, reviews, conversation and inline comments (including whether each thread is resolved or outdated), checks, and the log of each failing job. It records the PR head SHA next to the local HEAD. It treats every comment as a claim to check against the code, not an order, and classifies it:

ClassMeaningWhat happens
FIXa real defect or a requested change that fits the ticketgoes to the fix round
ALREADY DONEthe code already does itreply cites file:line
QUESTIONthe code is fine; the reviewer asksanswer prepared
DISAGREEthe change would be wrongreply with the evidence
OUT OF SCOPEvalid, not this ticketfollow-up ticket title prepared
CRITERION CHANGEchanges an acceptance criterionrun stops: the plan is revised first
CI REAL / CI FLAKY / CI INFRAa failure this change causes / a listed flaky test / runner or networkonly CI REAL goes to the fix round

Verdict FIXES NEEDED → fix round → code review → verify → git texts. PLAN CHANGE NEEDED or NOTHING TO FIX stop the run. Replies are prepared in <t>-pr-feedback.md and never posted.

Several tickets in one run

  1. Overlap check (ticket-overlap, planner with the Artifact tool). It maps each ticket's surface: files, modules, tables, routes, configuration and behaviour. Then it classifies every pair as independent, shared-files, dependent or same-work, with file:line. It decides which ticket is stacked on which, which ticket owns each piece of shared code, and whether the given order conflicts with a dependency. Report: overlap-<t>-<t>.md. Same work or an order conflict stops the run.
  2. Parallel planning. Every ticket gets its own plan agent and its own review/revise loop, all at once. Each planner gets a batch note: read the overlap report first and stay in this ticket's scope. Where the report gives a piece to another ticket, depend on it instead of doing it twice. A stacked ticket plans on top of the other ticket's planned changes. Any plan that does not pass gate 1 stops the batch, with acceptPlans ready in resumeArgs. That list also holds tickets whose planner or reviewer returned nothing, and resuming with it skips their plan review: read it before passing it back.
  3. Branch step. Before each ticket, an implementer agent runs only the branch step. It checks for a clean tree, runs git fetch, and for a stacked ticket checks that the parent branch has commits. Then it runs git switch -c task/<n>-<slug> <base>. The base is the base branch, or the parent ticket's branch. The guard allows this one git write, only for this role, only with the profile's branchPattern, and only on a clean tree.
  4. Build, review, verify, git texts, retro, as in ticket mode. If the stacked base moved under the plan, the run first does one refresh round, review plus revision, against the new base and then builds. If the refreshed plan still has open Critical or High findings that the planner rejected, the run stops. The plan's base SHA is not moved by the refresh, so a stacked ticket can stop at base-moved again.
  5. Stop for the person. When a ticket is green, the run stops with awaiting-go. The person reads the diff, commits on that branch, and resumes the run with resumeFromRunId and the returned resumeArgs (go + 1). Everything already done comes from the workflow's cache. The cache lives in the session that ran the workflow.

The guard

A PreToolUse hook on Bash|Write|Edit|NotebookEdit. It acts only when the caller's agent type starts with pipeline-, or when a headless launcher set PIPELINE_GUARD_ROLE. Every other call, including the person's own session, passes untouched. A refusal is a deny with a reason the agent reads. The agent instructions say a refusal is not something to route around: do it the named way or report a blocker. An error inside the checks refuses. A hook that cannot start, times out (10 s, while the guard may wait up to three 5 s git calls) or exits with an error lets the call through, because Claude Code treats those as non-blocking; malformed input is let through on purpose.

Refused for every pipeline agent

  • git commit, push, merge, rebase, cherry-pick, revert, am, tag, stash (except list/show), reset --hard, clean -f, checkout -- <path>, restore, apply (no patch files), branch writes
  • GitHub writes: gh pr/issue/release/repo/workflow/run/label/… write verbs, gh api with a non-GET method, fields without -X GET, gh api graphql mutations, curl writes to github.com
  • Docker prunes and volume removal; stop/rm/restart/compose down of protected stacks; SQL writes via docker exec into them
  • a profile-listed destructive command that names a shared port, or names no target at all (it would fall back to .env defaults)
  • anything in the profile's denyAlways

Who may write what

  • plan-reviewer, code-reviewer, verifier, pr-feedback: only their own report (*-plan-review.md, *-code-review.md, *-verify.md, *-pr-feedback.md) and scratch dirs; no in-place edits (sed -i, prettier --write, eslint --fix, patch)
  • retro: only pipeline-runs.jsonl, pipeline-lessons.md, *-retro.md
  • learner: only repo-knowledge.md, repo-pulse-state.json, repo-pulse-<date>.md
  • planner, implementer: anywhere in the repository except .git/ and .claude/
  • only the implementer may create a branch: exactly switch -c / checkout -b, a name matching branchPattern, a clean tree
  • scratch (/tmp, $TMPDIR, /var/folders) is always writable

Shell commands are tokenized, so a quoted > in SQL or a grep 'git push' is not mistaken for a redirect or a push. Leading wrappers such as env, sudo, time, nohup, nice, caffeinate and timeout are stripped with their options, the scripts inside bash -c and eval are checked too (unless the quoted script contains a redirect), heredoc bodies are treated as data, and cd is tracked when resolving relative redirect targets. A command that cannot be tokenized gets a stricter regex check. Writes are checked for the Write and Edit tools, shell redirects, tee and the common in-place editors; rm, cp, mv, sed --in-place or a script that writes a file are not. It is a guardrail for agents that follow instructions, not a sandbox.

The report check

A SubagentStop hook. When a report agent tries to finish, the hook checks that the agent wrote its report during this run and that the report's latest section contains the lines below. If something is missing, the hook blocks the stop once, and its reason becomes the agent's next instruction. A second stop is never blocked, so an agent that stopped on purpose can say so and finish. It takes the ticket number from the first user entry of the agent's transcript, which is the request relayed to the workflow; when that names several tickets or none, it checks the newest fresh report, which in a parallel batch can belong to another ticket.

Context per agent

Every turn re-reads the agent's whole context, so whatever an agent carries is paid for on every turn. Four measures cut that down without changing what any phase reads or decides:

  • A tool allowlist per agent type: Read, Bash, Edit, Write, WebFetch, WebSearch, Agent, ToolSearch, Monitor, TaskStop, AskUserQuestion, ListAgents. These are the tools pipeline phases had actually used. Measured first-turn context: 42,954 tokens with every tool (96 agents), 21,706 to 22,030 with the list. Agent and Monitor stay in every list; a subagent an agent starts is guarded only if it is itself a pipeline type.
  • The Artifact tool only where needed. With it, the planner's first-turn context is 27,621 tokens (17 agents), about 6k more than a lean agent. The first planner always has it and reports every link it finds. Later phases get the -artifacts variant only when there is a link. A lean agent that meets a link stops before doing anything and returns needsArtifactTool, and the workflow restarts that step with the variant.
  • Pointers in fix-round prompts: the failing tests, open finding ids, criteria not closed. The agent still reads the report, but it knows where to look.
  • Independent read-only calls in one turn. Measured result: this one did not work (see Numbers).

Learning loops

Retro, after every run

Numbers it does not estimate: runstats.py reads the transcripts and gives, per pipeline agent, minutes, turns, tool calls, first and peak context, token sums (largest usage per message id), and the guard events the agent hit.

Escapes: a defect found by a later phase that an earlier phase was responsible for. Examples: a code-review finding about the plan's design (plan review missed it), a verify failure in code that review closed, a PR item classified FIX or CI REAL. For each escape, the retro names the one check that would have caught it. Flaky tests and environment problems are listed separately; they are not escapes.

Lesson lifecycle:

  1. candidate: one ticket of evidence, a rule, a target (profile section or skill step) and retire_when.
  2. proposed: evidence from two tickets. The retro writes the exact edit, quoting the text it replaces as it stands now, so the edit applies.
  3. adopted: only a person applies the edit and marks the lesson with the date.
  4. Retirement proposed when the lesson has been adopted for 10+ runs and its check never appears again, so the skills do not only grow.

It also records whether the tree that was committed is the tree that went GREEN (verifiedTreeIsFinalTree).

/pipeline-retro digest 7 gives the weekly trend; it says when fewer than 3 runs are too few to read one.

Repo pulse, weekly

Triage without tokens: prscan.py lists every PR merged into the base since the last pulse, using git plus one read-only gh call.

  • High (read in full): the PR changes the instruction files, the runtime version or build/lint config, adds a migration or a guard test, removes a module, moves a dependency's major version or a script people run, or deletes a path a memory note names.
  • Medium (title and signals): docs, CI, platform or config changes.
  • Low (counted).

It also lists which memory notes and profile lines name a path a high PR changed.

The learner agent reads the high PRs, writes what is now true into repo-knowledge.md ## Now with a PR or file for every fact, and learns team conventions from review comments. A convention counts only when the same request appears on two PRs or comes from two reviewers. Stale memory notes, profile lines and lessons come back as exact proposed edits.

Runs headless via run-repo-pulse.sh under the guard as pipeline-learner, from a launchd job the person installs. A cloud schedule cannot do this job: it cannot see local memory, the profile or the work directory.

Limits worth saying out loud

  • The workflow trusts the verdicts and counts its agents report. A workflow script cannot read files, so there is no deterministic check of a report; the separation of agents is the check.
  • When gate 1 closes with Medium or Low findings open, the last fold is not re-reviewed. Gate 2 is where a person sees it. It happened in every v3 ticket; one escape in nineteen traces directly to it.
  • Fix rounds after RED skip code review. A round after a GREEN makes that GREEN stale; the implementer has to say so and name verification as the next step.
  • Implementations share the open checkout: one at a time, and no commits while a review or a verify run is reading the tree.
  • The guard parses commands; a determined process could still write files in ways it does not parse.
  • Resume works from the workflow's cache, which lives in the session that ran it. A call whose prompt has not changed returns its cached result, so resuming after BLOCKED or base-moved replays the stop unless something in the call changes.
  • Implementations share the open checkout and its branch; most unplanned stops came from branch, checkout or session state, not from the code.
  • runstats.py does not see agents that a workflow started; the retro measures them from the run directory by hand.
  • New agent types and skills load when a session starts.

Where the saving comes from (estimate)

  • Fewer turns: about three fifths. Turns fell from 71 to 30. Narrower roles, no suites before Verify and pointers in fix prompts all cut turns; these data cannot separate them.
  • The tool allowlist: about an eighth. First-turn context is 42,954 tokens with every tool, 21,706–22,030 with the allowlist, 27,621 for the planner with the Artifact tool. The roughly 21k removed is carried on every turn.
  • Smaller working context per turn: the rest. Cache reads per turn fell from 133k to 73k; tool definitions explain 21k of that.
  • Fix-prompt pointers: at most about 9 points of the fix-round drop, the gap between fix rounds (−77%) and implementation (−68%).

The plan gate

Before: review rounds per ticket were 1, 2, 4, 4, 5, 9 and 10 (by the review files; median 4). Two plans were accepted by a person after the cap, two closed the gate only inside ad-hoc follow-up scripts, two passed the first version's self-certifying gate (one of them after an ad-hoc amendment), and for one the outcome cannot be read from the records. There was no acceptPlan.

v3: the gate closed by itself in all 13 tickets, 11 in the first round, one in the second, one in the third. acceptPlan was never used. The price: when the gate closes, Medium and Low findings are folded and not re-reviewed. That happened in 13 of 13 tickets. Of the 19 escapes from v3 runs, 1 traces directly to such an un-re-reviewed fold, 5 sit in the same text or code with a different defect, and 13 were never raised by plan review at all.

What did not work

  • Telling agents to send independent reads together changed almost nothing: among the agents that carry the rule, multi-call turns went from 9.2% to 8.3%.
  • Planning got 76% more expensive per agent.
  • The checkout is shared: 6 of 17 unplanned stops came from branch, checkout or session state.
  • Resuming a stopped run replays a cached BLOCKED or base-moved result unless the person changes the call; both times it mattered, it was worked around by hand.
  • Until 5 November, long local integration runs failed on expired test tokens and host sleep, and fix rounds were spent on them. The fixes are on this page; no real run has used them yet.

Method and caveats

  • Tokens: assistant usage from the transcripts, the largest value per message id. Context = input + cache reads + cache writes of a request. Every agent transcript in a run directory is counted, including restarted agents.
  • Cost index = input + 0.1 × cache reads + 1.25 × cache writes + 5 × output, in input-token units at list-price ratios. It compares runs; it is not a bill.
  • Output is under-recorded in the earlier versions' agent transcripts, so they look cheaper than they were.
  • A resumed workflow keeps its run id and its record shows only the last invocation, so time is measured from agent transcripts, not from the record's duration.
  • Transcripts older than about 30 days are deleted; the hand-routed era is partly measured from a 20 October snapshot.
  • Ticket sizes differ and N is small (7 tickets before, 13 in v3). Medians are compared.
